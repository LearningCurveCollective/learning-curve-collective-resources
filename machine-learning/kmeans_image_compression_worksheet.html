An Image Is a 3-D Array of Numbers

Our running example is a photograph of bell peppers — the classic test image for color compression, with red, green, and yellow peppers against a dark background (a scene chosen because it has a few strongly distinct color families, which is exactly what makes it interesting to compress). When you run A = imread('peppers.tiff'), the variable A is that image, stored as one 3-dimensional array of shape $512 \times 512 \times 3$: rows $\times$ columns $\times$ color channels. Reading an entry $A[i,\,j,\,c]$ drills down in three stages:

$i$ picks the row and $j$ picks the column — together $(i,j)$ selects one pixel location on the grid.

At that location, three color values are stored: an amount of red, of green, and of blue.

$c \in \{0,1,2\}$ picks which of the three you want: $$A[i,\,j,\,0] = \text{red value}, \qquad A[i,\,j,\,1] = \text{green value}, \qquad A[i,\,j,\,2] = \text{blue value}$$

So $A[100,\,350,\,1]$ reads: “at the pixel in row 100, column 350, give me the green value” — and the full color of that one pixel is the slice A[100,350,:], a triple like $(187,\,43,\,51)$.

Why 0–255? Each value is stored in 8 bits (8 binary digits), and 8 bits can express $2^8 = 256$ distinct patterns — hence the range $\{0, 1, \dots, 255\}$. The value itself is not binary; its storage is: eight digits’ worth per channel. Three channels $\times$ 8 bits $= 24$ bits per pixel — the number the compression factor (to be shown in tab 4) will be measured against.

Two useful ways to slice the same array: A[i,j,:] is one pixel, all channels (a point in $\{0,\dots,255\}^3 \subset \mathbb{R}^3$ — the object K-means will cluster), while A[:,:,0] is all pixels, one channel (a full $512\times512$ plane of red intensities — the panels on the right below).

The key reframe for this whole problem: compression will ignore the grid entirely. Each pixel becomes just a point $(r,g,b) \in \mathbb{R}^3$ — position $(i,j)$ is remembered only so we can put colors back at the end. Two pixels from opposite corners with the same color are the same point in color space. Head to tab 2 to see the image forget its shape.

Common misconception: channels are components, not categories. The third axis does not sort pixels into “red ones, green ones, blue ones,” and a pixel does not hold one color label. Every pixel owns all three values simultaneously — they are mixing amounts, combined additively by the display: $(255,0,0)$ is pure red, $(255,255,0)$ is yellow (red + green light), $(180,180,180)$ is gray. So A[:,:,0] is the red component of every pixel — a full $512\times512$ plane with one entry per pixel — not “the subset of pixels that are red.” Test yourself on the inspector above: click a yellowish pixel and confirm it lights up both the red and green planes with large values. If the channels were categories, a pixel could appear in only one plane — but every click lands in all three.

Forget the Grid: Pixels as Points in $\mathbb{R}^3$

What this plot is: every pixel of the demo image, plotted as a point in $\mathbb{R}^3$ as a function of its color values. Each axis is one feature — R, G, B — and a pixel’s coordinate along each axis is its stored intensity in that channel. The pixel is the point; nothing else is computed.

What’s lost: within this representation, location is gone — the point cloud alone cannot rebuild the image, because nothing in it says where any color came from.

On the left, the full 3-D cube $[0,255]^3$ (drag it to rotate); on the right, one 2-D face of the same cube at a time (a projection — we drop one coordinate to draw flat).

Two footnotes on the loss: the grid isn’t destroyed — the array still has it, and pixel order is kept off to the side so centroid colors can be painted back afterward; the clustering simply never consults it. And multiplicity collapses too: fifty identical background pixels land on the same dot, so a small-looking clump can carry huge weight in the distortion $J$.

Notice the structure: the points are not uniformly scattered. They gather into a handful of clumps — the reds of the peppers, the greens of the stems, the dark shadows. That clumpiness is the entire reason compression works: if most pixels crowd around a few colors, a few well-chosen representative colors can stand in for all of them.

What the cube is, and what $k$ does to it. The cube is the space of every possible color — all $256^3 \approx 16.8$ million values a pixel could take. Our image occupies only a tiny, clumpy corner of that vast space, and a dense clump means “many pixels want approximately this color.”

$k$ is how many colors we reduce that entire space of possibility down to: K-means (tab 3) drops $k$ representative points into the cloud, and after compression those $k$ points are the only colors that exist — 16.8 million possibilities collapsed onto 16 chosen ones, placed where the clumps actually are. The grid position of each pixel plays no role — the whole reduction happens purely in color space.

Before tab 3: what exactly is a centroid?

A center of mass. A centroid $\mu_j$ is the balance point of the pixels assigned to cluster $j$ — and since every pixel weighs the same, the center of mass is just the component-wise mean:

$$\mu_j = \frac{1}{|C_j|} \sum_{i \in C_j} x^{(i)} \qquad \text{— average the R values, the G values, and the B values separately}$$

Three averages, one point. Note what that makes it: a color (a point in the cube), and generally one that appears nowhere in the original image — a synthesized compromise at the middle of its clump.

The number of centroids is a choice, not a discovery. $k$ is a hyperparameter: set before the algorithm runs, not learned by it. The choice $k = 16$ is partly a quality/size tradeoff — and, more cleanly, follows from $16 = 2^4$: each pixel’s index then fills exactly 4 bits with no waste.

The source of the $\log_2 k$ is a one-line counting argument: $b$ bits can spell $2^b$ distinct patterns, so naming each of $k$ palette entries requires the smallest $b$ with $2^b \ge k$, i.e. $b = \lceil \log_2 k \rceil$ bits per pixel. That’s the minimal index width forced by counting (derived properly in tab 5’s compression-factor section, and shown live in tab 4’s readouts as you switch $k$). Powers of 2 are the natural palette sizes because the ceiling is then exact — no wasted patterns.

The assignment rule: each pixel takes on the color of its nearest centroid (Euclidean distance, in RGB space). Note the circularity: the centroid is the mean of the pixels assigned to it, while assignment is “nearest centroid” — each definition needs the other one first. That chicken-and-egg is precisely why K-means iterates: tab 3 breaks the circle by alternating the two, one half-step at a time.

3

K-Means, One Move at a Time

K-means alternates two half-steps, each of which you can fire by hand below. Both are exact minimizations of the same objective, the distortion

$$J(c, \mu) = \sum_{i=1}^{n} \big\| x^{(i)} - \mu_{c^{(i)}} \big\|^2$$

where $x^{(i)}$ is pixel $i$’s color, $c^{(i)}$ is its cluster assignment, and $\mu_1, \dots, \mu_k$ are the centroids. Note the two separate counts: $n$ is the number of pixels (576 here) and $k$ the number of centroids (2–16 here) — the sum runs over pixels, and $k$ enters only through the assignment’s range, $c^{(i)} \in \{1,\dots,k\}$. The subscript $\mu_{c^{(i)}}$ reads inside-out, like mu[c[i]]: look up pixel $i$’s cluster number, then fetch that cluster’s centroid. Assign minimizes $J$ over the assignments $c$ with centroids frozen; Update minimizes $J$ over the centroids $\mu$ with assignments frozen. Watch $J$ in the readout: it must fall (or stall) on every half-step — that monotone descent is the convergence proof, live.

Two nested minimizations, solved inside-out. Each half-step is an inner minimization in closed form: Assign is a per-point nearest-centroid argmin (the same closest-point structure as orthogonal projection), and Update uses the fact that the mean is the argmin of summed squared distances (one line of calculus — derived in tab 5). K-means is coordinate descent that alternates the two. It converges because $J$ decreases every half-step and is bounded below — but only to a local minimum, which is why re-clicking Initialize can land you a different (sometimes worse!) final palette. Try it.

How territories are determined

The Assign step never draws borders explicitly — the nearest-centroid rule is the map. Centroid $j$’s territory (its Voronoi cell) is simply the set of locations whose nearest centroid is $\mu_j$:

$$R_j = \{\, x : \|x - \mu_j\| \le \|x - \mu_\ell\| \text{ for all } \ell \neq j \,\}$$

The border between two territories is the perpendicular bisector of the segment joining their centroids (points equidistant from both); with $k$ centroids, each cell is the intersection of its pairwise wins — a convex region with flat walls. The canvas below paints every location by its nearest centroid, which is the same computation the Assign step performs. Drag the centroids: each territory follows its centroid, and every border remains the bisector between the two dots it separates.

Border pixels are the reassignment zone: a point deep inside a cell is firmly claimed, while a point near a wall is nearly tied and flips allegiance under a small centroid movement — the microscopic mechanism behind each Assign step’s reclaiming of points.

Initialization, and where the loop starts: each centroid begins at the $(r,g,b)$ of a randomly chosen pixel — a random data point, not a random location in the cube, so every centroid starts inside a populated region. The alternation then refines: territories drawn from the centroids, centroids moved to the means of their territories, territories redrawn — until map and means agree. The resting point is a local minimum of $J$: different random starts can flow into different valleys, which is what re-clicking Initialize demonstrates. Standard remedies in practice: several random restarts keeping the lowest-$J$ run, or spread-apart seeding (k-means++).

The full life of a run

The converged solution is not unique. Convergence means arriving at a local minimum of $J$ — a configuration no single half-step can improve — not the global one. Different random initializations flow into different valleys and end at different (usually similar, occasionally worse) palettes.

4

Compression = Replace Every Pixel with Its Centroid

The palette is the final centroids. The $k$ centroids that K-means converged to in tab 3 become the compressed image’s entire color vocabulary: every pixel of the output is one of these $k$ colors, no exceptions. The compressed image then stores two things: that palette (the $k$ centroid colors, 24 bits each, stored once) and, per pixel, an index saying which palette entry to use. Decompression is a lookup: index $\to$ palette entry $\to$ paint that color.

What one pixel stores — before: three 8-bit channel values $(r, g, b)$, each in $\{0,\dots,255\}$  $\Rightarrow$  $3 \times 8 = 24$ bits (one of $256^3 \approx 16.8$ million colors).

After: no channel values at all — a single index in $\{0, \dots, k-1\}$  $\Rightarrow$  $\lceil \log_2 k \rceil$ bits (one of $k$ palette entries). The full-precision color lives in the codebook, not in the pixel. In one line: $k$ centroids means $k$ possible answers to “which one?”, and $\lceil \log_2 k \rceil$ bits is the cost of writing an answer down.

Not per-channel quantization. Reducing to 16 colors does not mean each channel now takes 16 levels — that would impose a rigid $16^3 = 4096$-color grid at $3\times 4 = 12$ bits/pixel. K-means instead places its 16 representative points anywhere in the cube, wherever the data’s clumps actually are — which is why 16 well-chosen colors can beat thousands of grid-imposed ones for a particular image.

What to notice as $k$ drops: smooth gradients develop visible banding (a gradient that used dozens of colors now steps through two or three), and rare colors get absorbed into common ones. That lost detail is exactly the distortion $J$ — the compression is lossy, and the loss is the very quantity K-means minimizes. The algorithm literally chooses the $k$-color palette minimizing the total squared error of the compression: objective and application are the same number. Also worth noticing: the factor only improves logarithmically — halving the palette from 16 to 8 colors saves just 1 bit per pixel.

5

Why Each Half-Step Is an Exact Minimization

0

The plan. We show K-means is coordinate descent on the distortion $J(c,\mu)$: the Assign step is the exact minimizer of $J$ over assignments $c$ with $\mu$ frozen, and the Update step is the exact minimizer over centroids $\mu$ with $c$ frozen. The second claim needs a one-line calculus lemma (the mean minimizes summed squared distance). Monotone descent plus a bounded-below objective then gives convergence.

1

Assign minimizes over $c$, centroids frozen. $J$ is a sum of per-pixel terms, and pixel $i$’s term $\|x^{(i)} - \mu_{c^{(i)}}\|^2$ depends only on its own assignment $c^{(i)}$. So the sum is minimized by minimizing each term separately:

$$c^{(i)} \leftarrow \arg\min_{j \in \{1,\dots,k\}} \big\|x^{(i)} - \mu_j\big\|^2$$

— nearest centroid wins, and no other assignment can do better. (A per-point inner argmin with everything else held fixed — the workhorse pattern of alternating algorithms.)

2

Lemma: the mean is the argmin of summed squared distance. Fix the points $z^{(1)},\dots,z^{(m)}$ assigned to one cluster and consider $h(\mu) = \sum_{s=1}^m \|z^{(s)} - \mu\|^2$. Take the gradient in $\mu$ (each term by the chain rule on $\|w\|^2 = w^Tw$):

$$\nabla_\mu h = \sum_{s=1}^m 2\,(\mu - z^{(s)})$$

Set to zero and solve — split the sum and count the $m$ copies of $\mu$:

$$m\,\mu = \sum_{s=1}^m z^{(s)} \;\;\Longrightarrow\;\; \mu^* = \frac{1}{m}\sum_{s=1}^m z^{(s)}$$

The Hessian is $2m\,I \succ 0$ (strictly positive definite — not merely PSD), so $h$ is strictly convex and $\mu^*$ is the unique global minimizer.

3

Update minimizes over $\mu$, assignments frozen. With $c$ fixed, $J$ splits into $k$ independent pieces — one per cluster, each of the form $h$ above over that cluster’s points. By the lemma, each piece is minimized by that cluster’s mean:

$$\mu_j \leftarrow \frac{1}{|C_j|}\sum_{i \in C_j} x^{(i)}, \qquad C_j = \{\,i : c^{(i)} = j\,\}$$

4

Convergence. Each half-step replaces its block with an exact minimizer, so $J$ never increases: $J_0 \ge J_1 \ge J_2 \ge \cdots$. Since $J \ge 0$ (a sum of squares), the sequence is monotone and bounded below, hence converges. Moreover there are finitely many possible assignments $c$, so the algorithm reaches a fixed point — a configuration no single half-step improves — in finitely many steps. Note carefully what this does not say: nothing here claims the fixed point is unique or globally optimal.

$$\boxed{\;\text{Assign and Update each exactly minimize } J \text{ in one block} \;\Rightarrow\; J \text{ descends monotonically to a local minimum}\;}$$

Non-uniqueness is proved the way uniqueness claims are always disproved — by counterexample: exhibit two distinct fixed points for the same data.

Data: the corners of a $4 \times 1$ rectangle — $(0,0),\ (4,0),\ (0,1),\ (4,1)$ — with $k = 2$.

A is fixed: centroids $(0, \tfrac12)$ and $(4, \tfrac12)$ are the means of their pairs, and each point’s own centroid (distance $\tfrac12$) beats the other ($\sqrt{16.25} \approx 4.03$) — Assign changes nothing, Update changes nothing.

B is also fixed: centroids $(2,0)$ and $(2,1)$ are the means of their pairs, and each point’s own centroid (distance $2$) beats the other ($\sqrt{5} \approx 2.24$) — again neither half-step improves anything.

Conclusion: two fixed points for the same data, with $J = 1$ versus $J = 16$ — and initialization decides which valley the descent flows into (seed the centroids near the top and bottom edges, and the first Assign produces split B, from which the algorithm never escapes). The stepper’s re-Initialize behavior is the empirical face of this; the rectangle is the proof.

6

Part (b): The Compression Factor

1

Bits per pixel, before. Before compression, the “palette” is every representable color: each channel takes one of $256$ values, so the full palette has $256^3 \approx 16.8$ million entries. Naming one entry among $256^3$ costs

$$\log_2\!\big(256^3\big) = 3\,\log_2 256 = 3 \times 8 = 24 \text{ bits/pixel}$$

— the familiar “three 8-bit channels” is this same number sliced per channel: $\log_2 256 = 8$ bits for each of R, G, B. Over the whole image: $262{,}144$ pixels $\times$ 3 bytes $= 786{,}432$ bytes.

2

Bits per pixel, after. Compression shrinks the palette: from the full $256^3 \approx 16.8$ million representable colors down to the $k = 16$ centroid colors. A compressed pixel therefore stores only an index into that 16-entry palette — and the same counting argument as Step 1, run on the smaller palette, prices the index. Each bit of the index is one yes/no answer that halves the remaining candidates — twenty questions, played against the new palette of $k$ colors instead of the original $256^3 \approx 16.8$ million.

WORKED EXAMPLE — a pixel whose palette index is 13, with $k = 16$:

candidates 0–15  —  “top half (8–15)?” yes → 1  —  8–15
8–15  —  “top half (12–15)?” yes → 1  —  12–15
12–15  —  “top half (14–15)?” no → 0  —  12–13
12–13  —  “is it 13?” yes → 1  —  13. Done: transcript $\mathbf{1101} = 13$ in binary.

Back to the general argument. The stored bits are the answer transcript — binary representation is the halving game written down. Since each answer at best halves the pool, $b$ answers distinguish at most $2^b$ entries, so pinning down one of $k$ requires the smallest $b$ with

$$2^b \ge k \;\;\Longleftrightarrow\;\; b = \lceil \log_2 k \rceil$$

For $k = 16$: $2^4 = 16$ exactly — the game ends on question 4 with nothing wasted, so $b = 4$ bits/pixel. (A non-power-of-2 palette, say $k = 10$, still costs 4 questions, but some transcripts name entries that don’t exist — the wasted patterns that make powers of 2 the natural palette sizes.)

3

Calculating the compression factor

Take the ratio — this is the answer to part (b). Steps 1 and 2 are the same counting argument applied to two palettes — one of size $256^3$, one of size $k$ — so the factor is one formula evaluated twice:

$$\text{factor} = \frac{\log_2\!\big(256^3\big)}{\log_2 k} = \frac{24 \text{ bits/pixel}}{4 \text{ bits/pixel}} = 6$$

4

Why “approximately”: the codebook. The file must also ship the palette itself: $16 \times 24 = 384$ bits $= 48$ bytes, against $131{,}072$ bytes of indices — overhead $\approx 0.04\%$, negligible.

$$\boxed{\;\text{compression factor} \approx 6\times \quad (786{,}432 \text{ B} \;\to\; 131{,}072 \text{ B} + 48 \text{ B codebook})\;}$$

Note the structure of the argument: the factor is a pure bits-per-pixel computation, $24 \to \log_2 k$, independent of image size (size only shrinks the codebook’s relative overhead further). When writing this up, the two-line bits-per-pixel derivation is the answer — a bare “6” shows the result but not the reasoning.

Going deeper (optional): the $\log_2$ is information theory knocking. Our 4-bit scheme gives every palette index the same length — and that’s only optimal if all 16 colors are equally common. They aren’t: the color-space clumps in tab 2 have very different sizes. Information theory makes this precise. If color $j$ occurs with probability $p_j$, the cheapest possible average encoding length is the entropy

$$H = \sum_{j=1}^{k} p_j \log_2 \frac{1}{p_j} \;\; \text{bits per pixel}, \qquad \text{with } H \le \log_2 k$$

and equality exactly when all $p_j = \tfrac{1}{k}$ (the uniform case). Read $\log_2 \frac{1}{p_j}$ as “rare colors deserve long names, common colors short ones” — the trick behind Huffman coding, and the reason real formats (PNG, ZIP) compress the index stream a second time after quantization. So our factor of 6 is a floor, not a ceiling: K-means shrinks the palette, entropy coding then shrinks the indices. Two different ideas of redundancy, stacked.

Check Yourself

1

Palette size. What is the compression factor for $k = 256$ colors? For $k = 2$? What pattern do you notice in how the factor grows as $k$ shrinks?

$k=256$: $\log_2 256 = 8$ bits/pixel, so factor $= 24/8 = 3\times$.   $k=2$: $\log_2 2 = 1$ bit/pixel, so factor $= 24/1 = 24\times$.

Pattern: the factor is $24/\log_2 k$ — each halving of the palette saves only 1 bit/pixel. Compression improves logarithmically in $1/k$, so shrinking an already-small palette buys big factors (at big quality cost), while trimming a large palette barely helps.

2

The sqrt shortcut. Your Assign step compares $\|x^{(i)} - \mu_j\|^2$ without ever taking a square root. Is the code still correct? Justify with a general optimization principle.

Yes. $t \mapsto \sqrt{t}$ is strictly increasing on $[0,\infty)$, so $\|x - \mu_a\| < \|x - \mu_b\| \iff \|x-\mu_a\|^2 < \|x-\mu_b\|^2$: the argmin is unchanged by a strictly monotone transform of the objective — the same principle that lets you add constants or apply positive scaling to an objective without moving its optimizer. (Bonus: skipping the root is also faster.)

3

Empty cluster. During iteration, centroid $\mu_5$ attracts zero pixels. What goes wrong in the Update step as coded naively, and name one reasonable fix.

The update divides by the cluster size $|C_5| = 0$ — a division by zero (in NumPy, a silent NaN that then poisons every later distance computation). Reasonable fixes: re-seed $\mu_5$ at a randomly chosen pixel; or drop the cluster; or assign it the point farthest from its current centroid. The subtle danger: with $k=16$ on $16{,}384$ points the case may never trigger in testing, leaving a latent bug — handle it anyway.

4

Lossy, precisely. In one sentence each: (a) exactly what information does the compressed file lose, and (b) what mathematical quantity measures the total loss?

(a) Each pixel’s residual from its palette color — the vector $x^{(i)} - \mu_{c^{(i)}}$ is discarded, so all pixels in a cluster become indistinguishable. (b) The distortion $J = \sum_i \|x^{(i)} - \mu_{c^{(i)}}\|^2$ — which is precisely the objective K-means minimizes: the algorithm picks the palette that loses the least (locally).

5

Why cluster a small image? A standard recipe learns centroids on a small, downsampled image but then compresses the full-size image of the same scene. Why is this legitimate, and what assumption does it rely on?

The centroids only need to represent the color distribution, not individual pixels — and the small image is (approximately) a sample from the same color distribution as the large one, since it depicts the same scene. Clustering $16{,}384$ points instead of $262{,}144$ buys a $16\times$ speedup at the cost of slightly noisier centroids. The reliance: if the small image were missing a color region present in the large one (say, no yellow pepper), that region would compress badly — the assumption is distributional match between the sample you cluster and the data you compress.
